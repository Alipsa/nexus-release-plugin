# v2.4.0: one plugin with optional combined releases

Status: implementation and local verification complete. The development version is `2.4.0-SNAPSHOT`. See [the verification record](verification/v2.4.0-single-plugin.md).

## Outcome

Publish only the original plugin ID, `se.alipsa.nexus-release-plugin`. Expose the existing combined-release workflow through its extension, so a root project can release multiple publications without applying `se.alipsa.nexus-release-all` or selecting a single `mavenPublication`.

There is already one implementation codebase/JAR. The extra plugin declaration creates a second public entry point and marker; removing it does not require merging the task implementations.

## Configuration contract

Keep existing single-publication configuration and behavior as the default. Add an opt-in `combinedRelease(Action<CombinedReleaseExtension>)` method to `NexusReleasePluginExtension`. Calling the block enables combined support; no separate `enabled` boolean is necessary. Register combined tasks before executing the configuration action, so they can also be configured inside or immediately after the block. Register them only once if the block is called repeatedly.

Add a pre-application root opt-out: `nexusReleasePlugin.rootSinglePublicationTasks=false` in the consumer's `gradle.properties` (default `true`). The plugin reads it only when applied to `rootProject`; subprojects ignore it even though Gradle properties are inherited. Read it through `project.providers.gradleProperty('nexusReleasePlugin.rootSinglePublicationTasks').orElse('true')`, so configuration-cache input tracking includes it. Validate it as a literal boolean. It suppresses root `bundle`, `release` and `clearModuleMetadata` registration and their publication/metadata wiring, while retaining the discovery tasks. Their extension task-provider references remain null when suppressed, and this is documented. Existing custom root `bundle`/`release` tasks are left untouched. A same-project single and combined workflow uses the default `true`. With `false`, setting a root `mavenPublication` does not restore suppressed tasks or their wiring; document that the publication remains available to ordinary publishing and discovery only. With `false` and no combined block, neither single-release nor combined-release tasks are registered; this is expected.

This switch must be read before task registration: an extension flag set after applying the plugin cannot prevent name collisions. Do not implement the opt-out by removing tasks, `onlyIf`, or deferred registration. Existing users retain plugin-application-time single-task registration and accessors.

Proposed Groovy DSL (combined-only root also sets the property above):

```groovy
plugins {
    id 'se.alipsa.nexus-release-plugin' version '2.4.0-SNAPSHOT'
}

nexusReleasePlugin {
    userName = providers.gradleProperty('sonatypeUsername')
    password = providers.gradleProperty('sonatypePassword')

    combinedRelease {
        sourceDirectory = layout.projectDirectory
        manifestFile = layout.buildDirectory.file('releaseAll/manifest.json')
        stagingDirectory = layout.buildDirectory.dir('releaseAll/staging')
        bundleFile = layout.buildDirectory.file('releaseAll/bundle.zip')
        receiptFile = layout.buildDirectory.file('releaseAll/bundle-receipt.json')
        recordFile = layout.buildDirectory.file('releaseAll/deployment.json')
    }
}

// Repository-specific discovery and preparation remain explicit.
tasks.named('releaseAllPlan') {
    // Configure revision, candidate descriptors/POMs and Portal fixture.
}
```

The block supports Groovy and Kotlin DSL through Gradle's standard Action API. Use this construction order to avoid circular initialization, including when consumer rules realize tasks eagerly during registration:

1. Create an internal shared-properties holder with final references to properties built through `objects.property`, `objects.fileProperty` and `objects.directoryProperty`. Set endpoint and parent credential/Portal URL conventions on those properties, using the parent passed explicitly to the registrar, before registering any task; leave shared paths unset as specified below.
2. Register the six tasks. Each registration action wires task-property conventions directly from the already existing shared-properties holder. These actions must work immediately during `register()` as well as during later realization; they never depend on a nested extension or a mutable reference to one. Gather the returned typed providers in an immutable task-providers holder.
3. Create the decorated nested extension with `objects.newInstance(CombinedReleaseExtension, sharedProperties, taskProviders)`, using an `@Inject` constructor that receives the two holders plus `ObjectFactory`. Do not use `new`. Expose the shared holder's properties through getters and initialize the read-only task-provider fields from the provider holder. Both holders and all property/provider references remain final; the property's value can still be configured normally.
4. Return the nested extension to the parent registrar caller, store it privately, then execute the consumer's combined configuration action. Changes made by that action propagate through the already wired property conventions, even if a task was realized earlier.

The plugin does not eagerly realize tasks itself, but must tolerate eager consumer `tasks.withType(Type) { ... }`, `tasks.all { ... }` and `tasks.whenTaskAdded { ... }` rules. Task actions must consume only their task properties, never either holder, the registrar or the extension. Verify provider assignment on both supported Gradle versions before adding any custom setters. Do not resolve credentials or other providers while configuring the build.

Keep the nested instance private. Do not expose `getCombinedRelease()` or a public field/property for it: the Action method is the only configuration entry point and always opts in before exposing the instance. All six nested task providers are initialized before the action runs, so build scripts cannot observe unregistered/null combined providers. Repeated block calls configure the same instance and already registered tasks.

Supply the configuration-only registrar through the parent constructor: `project.extensions.create('nexusReleasePlugin', NexusReleasePluginExtension, registrar)`, with an `@Inject` constructor receiving `(java.util.function.Function<NexusReleasePluginExtension, CombinedReleaseExtension> registrar, ObjectFactory objects)`. Store the callback in a `private final` field with no getter, setter or setter-shaped initialization method. Do not rely on `@PackageScope`: Gradle's dynamic Groovy DSL can invoke package-scoped setters. Verify that Gradle injects ObjectFactory alongside the supplied Function on both supported Gradle versions.

The callback captures only the registration helper and the required configuration services, and receives the parent extension explicitly as its Function argument. It creates the shared-properties holder, sets credential and Portal URL conventions from that argument, registers and wires the tasks, creates the decorated nested extension and returns it in the order above. The Action method calls `registrar.apply(this)` once, stores its result in the parent's private nested field and then executes the configuration action. Using a Function makes the parent dependency explicit: no later-assigned captured local, extension-container lookup, or callback-driven parent initialization method is needed. No callback-initialization method is exposed. Neither tasks nor task actions retain the callback or the extension.

Expose the six typed providers on the nested extension as `planTask`, `signingCheckTask`, `guardTask`, `prepareMavenTask`, `bundleAllTask` and `releaseAllTask`. Require explicit getters backed by `private final` fields initialized in the nested constructor, with no setters or writable Groovy properties. Build scripts may configure the referenced tasks but cannot replace the providers, including with null. The combined providers have distinct names from the parent single-publication `bundleTask`/`releaseTask`, avoiding DSL scope-dependent types and null behavior. No Project/TaskContainer injection into the extension is needed.

Combined registration deliberately occurs at the first block call. Groovy `tasks.named('releaseAllPlan')` and `bundleAll { }` must follow that call. Earlier convention scripts must use `tasks.withType(ReleaseAllTask).configureEach` (and the corresponding types for other tasks), which also handles later registration. Kotlin builds must use `tasks.named<ReleaseAllPlanTask>("releaseAllPlan")` after opt-in, or typed `withType<ReleaseAllPlanTask>().configureEach` before it. Do not promise generated `tasks.releaseAllPlan` accessors: the combined tasks do not exist during plugin application.

Shared combined properties are `sourceDirectory`, `manifestFile`, `stagingDirectory`, `bundleFile`, `receiptFile`, `recordFile`, `repositoryUrl`, `portalUrl`, `userName` and `password`. Use existing task defaults for endpoints. Combined credentials and Portal URL inherit conventions from the parent extension (`nexusUrl` supplies `portalUrl`); explicit combined or task settings override conventions. `repositoryUrl` defaults to `https://repo.maven.apache.org/maven2` and does not inherit `metadataBaseUrl`: metadata lookup and combined exact-publication availability probes are separate endpoints, and a proxy for one need not support the other. Consumers using a proxy for both must configure both explicitly.

All shared paths remain unset until configured; there are no new `build/releaseAll` or source-directory defaults. The example supplies explicit paths. Credentials remain unset unless inherited or configured. Portal URL inherits the parent's existing Central Portal default. Map conventions as follows:

| Shared property | Tasks receiving its convention |
| --- | --- |
| `sourceDirectory` | `releaseAllPlan`, `releaseAllGuard`, `releaseAllPrepareMaven`, `bundleAll`, `releaseAll` |
| `manifestFile` | All six combined tasks |
| `stagingDirectory` | `releaseAllPrepareMaven`, `bundleAll` |
| `bundleFile` | `bundleAll`, `releaseAll` |
| `receiptFile` | `bundleAll`, `releaseAll` |
| `recordFile` | `releaseAll` |
| `repositoryUrl` | `releaseAllPlan`, `releaseAll` |
| `portalUrl`, `userName`, `password` | `releaseAllPlan`, `releaseAll` |

Use extension-backed path providers rather than producer-task output providers for these conventions: sharing a path must not introduce implicit preparation dependencies into status-only resume. Document in `combined-releases.md` that discovery must run in a separate invocation: scheduling `releaseAllPlan` with a manifest-consuming guard, Maven-preparation or signing-check task without explicit ordering/dependencies can cause Gradle to report an implicit/missing dependency because the planner writes the same manifest those tasks read. Sharing conventions does not provide orchestration; do not automatically add planner dependencies to solve this, since resume must remain independent.

Wire shared values as task-property conventions, preserving direct typed-task configuration. Keep task-specific properties on the existing tasks, including candidate inputs, signing JSON, version JSON, fixtures, Maven helpers and resume ID. Do not infer candidates or orchestration dependencies from all subprojects. Preserve separate discovery invocations, caller-owned prerequisites and status-only resume behavior. Combined HTTP timeout behavior remains unchanged in this consolidation. README and the combined guide must explicitly state that parent `httpConnectTimeoutSeconds` and `httpRequestTimeoutSeconds` are not inherited by combined tasks: their CentralPortalClient uses defaults (30 s connect, 1800 s upload, 60 s small calls), releaseAll repository HEAD probes retain hardcoded 15 s connect/read timeouts, and PublicationStatus availability probes used by releaseAllPlan and releaseAll retain a hardcoded 15 s connect timeout and 30 s per-request timeout. The PublicationStatus request timeout is separate from the CentralPortalClient overall caller deadline. Shared credential/URL inheritance does not imply timeout inheritance.

## Implementation sequence

1. Add `CombinedReleaseExtension` and extract task registration from `ReleaseAllSupportPlugin` into an internal helper. Retain all six task names, types and existing defaults: `releaseAllPlan`, `releaseAllSigningCheck`, `releaseAllGuard`, `releaseAllPrepareMaven`, `bundleAll` and `releaseAll`. Create the shared-properties holder before registration, wire conventions directly from it within each registration action, and return an immutable holder of typed task providers. Construct the decorated extension only after those providers exist; no registration action may depend on that extension being initialized.
2. Connect the opt-in method to `NexusReleasePluginExtension` and the original plugin. Keep registration during configuration, without `afterEvaluate`, execution-time Project access or eager task realization. Task actions consume their existing detached inputs. Make repeated configuration idempotent and verify provider updates after the block still flow through conventions.
3. Implement the root registration opt-out above. Keep default single-publication tasks and automatic `signing`/`maven-publish` application unchanged. A combined-only root may leave `mavenPublication` unset: configuration, task listing, combined tasks and ordinary publishing must work. With the default registration enabled, requesting single-publication bundle/release work still reports the existing missing-publication error. With the root opt-out, those plugin tasks do not exist: unqualified selectors execute subproject tasks and any consumer-owned root tasks. Preserve metadata cleanup scoping and configuration-cache behavior. Allow single and combined workflows in the same project.
4. Remove the `combinedRelease` plugin declaration from `build.gradle` and delete `ReleaseAllSupportPlugin.groovy` and its public class. Update tests to apply the original ID and opt in through the extension. Keep the existing implementation artifact coordinates, original plugin marker, signing and publishing policy. Inspect generated publication metadata rather than altering the repository's publication arrangement incidentally.
5. Update `README.md`, `combined-releases.md` and `release.md` with the new DSL, shared-property precedence and migration instructions. Keep historical 2.3.0 notes and released-version examples intact until the new release is available. Rewrite the opening of `combined-releases.md` and the combined-support paragraph in `README.md` (currently around line 215), which describe the old separate-plugin design; a DSL substitution alone is insufficient. Add a 2.4.0 in-progress section when implementation lands.

## Migration

Replace `id 'se.alipsa.nexus-release-all'` with the original plugin ID and add `nexusReleasePlugin { combinedRelease { } }`. Combined-only roots must set `nexusReleasePlugin.rootSinglePublicationTasks=false` before application to preserve unqualified `bundle`/`release` selectors and custom root task names. Move named task configuration after opt-in or use the order-independent typed `configureEach` forms described above. Kotlin users must replace generated combined task accessors with typed named lookup. Include this Kotlin migration snippet (task-type imports are required):

```kotlin
import se.alipsa.gradle.plugin.release.*

plugins { id("se.alipsa.nexus-release-plugin") version "2.4.0-SNAPSHOT" }

// May appear before opt-in, including in a convention script.
tasks.withType<ReleaseAllPlanTask>().configureEach {
    // Configure task-specific inputs.
}
nexusReleasePlugin {
    combinedRelease {
        sourceDirectory.set(layout.projectDirectory)
        // Configure the remaining shared paths explicitly.
        bundleAllTask.configure { /* BundleAllTask configuration */ }
    }
}
tasks.named<ReleaseAllPlanTask>("releaseAllPlan") {
    // Named lookup must follow opt-in.
}
```

Existing typed-task property configuration can remain; move repeated paths and credentials into the block when useful. Explain that applying the original plugin also applies signing and Maven publishing, which the old combined-only entry point did not do.

Do not publish a new marker for the old ID in 2.4.0. Deleting the class also breaks class-based `apply plugin: ReleaseAllSupportPlugin`; migrate those consumers to the original ID and extension block. Existing released versions remain available. Consumers must migrate when upgrading; an alias would retain the second public ID and defeat the requested simplification. Matrix's external build and guide require the same migration, tracked separately from this repository's changes. Local composite consumers must migrate before testing this checkout.
