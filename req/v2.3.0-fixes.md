# v2.3.0 review fixes: implementation plan

This is the historical implementation plan for PR #7. Release preparation in PR #8 upgraded the wrapper to Gradle 9.8.1 and moved the compatibility matrix to Gradle 8.13 / 9.8.1 with JDK 17 / 21; the versions below describe the original plan.

Implementation and local verification are complete; see [the verification record](verification/v2.3.0-fixes.md). Merge, real Portal smoke testing and tagging remain rollout steps.

This plan fixes the findings from the repository review. The work is split into three phases by severity. Ship each phase as its own commit or PR so it can be reviewed and reverted separately.

| # | Finding | Severity | Phase |
|---|---------|----------|-------|
| 1 | No HTTP timeouts in `WsClient` | High | 1 |
| 2 | A single `release` status-poll error fails an upload that succeeded; misleading messages | Medium | 1 |
| 3 | The `\|\|` short-circuit in `BundleTask` drops later `.asc` files | Medium | 1 |

General rules:
- Do not restructure the code beyond what each fix needs.
- Every behavior fix gets a regression test that fails before the change and passes after it. API visibility changes and documentation edits need no standalone failing regression test.
- Run `./gradlew build` plus the compatibility matrix (`-PtestGradleVersion=8.13` and `9.4.0`) at the end of each phase.
- Each phase's commit adds its entries to `release.md` (see "Release notes" below). Document new extension properties in `README.md`.

## Phase 1: release reliability

### 1. Add timeouts and an overall request deadline to `WsClient`

**Files:** `WsClient.groovy`, new `TimeoutSettings.groovy`, `build.gradle`, `.github/workflows/ci.yml`, `CentralPortalClient.groovy`, `NexusReleasePluginExtension.groovy`, `NexusReleasePlugin.groovy`, `ReleaseTask.groovy`, `ReleaseAllTask.groovy`, `README.md`

**Background (Java timeout semantics):**
- `URLConnection.setConnectTimeout(0)` and `setReadTimeout(0)` mean *infinite*. Allowing `0` would therefore switch timeouts back off.
- The read timeout only applies to reads from the response stream. It does **not** bound writes of the request body. A server that stops reading during `postMultipart` can block `input.transferTo(out)` indefinitely. Neither timeout bounds the total length of a request either: a server that trickles one byte per interval never trips the read timeout.
- `HttpURLConnection.disconnect()` cannot be relied on to cancel a request from another thread. In OpenJDK 17, once response headers have arrived, `disconnect()` calls `inputStream.close()`. `MeteredStream.close()` then waits for the same `ReentrantLock` that a blocked `read()` holds. So a watchdog that calls `disconnect()` can itself block until the read timeout fires. On a shared scheduler thread it would also delay every other request's watchdog. Sources: `sun/net/www/protocol/http/HttpURLConnection.java` (`disconnect()`) and `sun/net/www/MeteredStream.java` (`read`/`close` take `readLock`) in jdk17u.

So the deadline must come from a mechanism that does **not** need to unblock the I/O thread before the caller can continue. The earlier `disconnect()`-watchdog design is withdrawn.

**Design rule:** the *calling thread* is bounded by waiting on a future with a timeout. Releasing the network resources is a separate property, and it must be proven by tests (see the proof gate below).

**Scope:** this finding bounds requests made through `WsClient`/`CentralPortalClient`, including single-publication upload and deployment polling, and combined upload/resume calls using that client. `releaseAll` receives these deadlines through `CentralPortalClient` with default values only; the new extension properties apply only to `release`. Two combined-flow availability checks remain unchanged and outside the overall deadline: `PublicationStatus.request()` uses a separate HTTP client, and the HEAD availability check in `ReleaseAllTask` uses `HttpURLConnection` with 15 s connect/read timeouts but no overall deadline. Do not claim that every Central Portal call in the combined flow is bounded. Extending the shared deadline mechanism to `PublicationStatus` is deferred.

**Mechanism A (primary): move `WsClient` to `java.net.http.HttpClient`.** `PublicationStatus` already uses that API, but does not receive this deadline implementation.
1. Send each request with `client.sendAsync(request, BodyHandlers.ofString())`. Wait with `future.get(remainingDeadlineMillis, MILLISECONDS)`. The future completes only after the whole response body has arrived, so the wait covers connect, the upload write, headers and body.
2. On `TimeoutException`: call `future.cancel(true)`, then throw `java.net.SocketTimeoutException("Request exceeded overall deadline of <n>s: <url>")`. The caller returns at the deadline whatever the I/O layer is doing. Whether `cancel(true)` also aborts the underlying exchange on JDK 17 (expected since JDK 16, JDK-8245462) is **unproven** until test T6 passes.
3. On `ExecutionException`, unwrap and rethrow the `IOException` cause. Restore the interrupt flag on `InterruptedException`.
4. Also set `HttpRequest.timeout(deadline)` as a second safeguard. It is not the primary bound.
5. Keep today's `HttpURLConnection` behaviour through explicit builder settings:
   - `.version(HttpClient.Version.HTTP_1_1)`, so there is no h2c upgrade on `http://` test URLs;
   - `.followRedirects(HttpClient.Redirect.NORMAL)`;
   - `.proxy(ProxySelector.getDefault())`, so `http(s).proxyHost` settings keep working;
   - `.connectTimeout(connectTimeout)`.
6. Multipart upload: `BodyPublishers.concat(ofByteArray(prefix), ofFile(bundle.toPath()), ofByteArray(suffix))`. This gives a fixed `Content-Length` and the same bytes on the wire as today. Existing `CentralUploadApiTest` assertions on the request must pass unchanged.
7. Keep the public `WsClient` method signatures, the result map keys (`BODY`, `RESPONSE_CODE`, `HEADERS`), and `WsException(status, errorBody)` for non-2xx responses. `HEADERS` will now come from `response.headers().map()`: lower-case names and no `null` status-line key. No code in the repository reads `HEADERS` (checked), but `WsClient` is public, so record the change in the release notes.
8. Create one `HttpClient` per `WsClient` instance; do not share a static client across builds.

**Mechanism B (fallback, used only if the proof gate fails for A on a supported JDK):** keep `HttpURLConnection`, but never cancel it through a shared thread.
1. Run each request on its own new daemon worker thread (`nexus-release-http-<n>`). The caller waits with `Future.get(deadline)` and throws the same `SocketTimeoutException` at the deadline.
2. Cleanup after a timeout runs on a separate, new daemon thread that calls `conn.disconnect()`. Neither the caller nor any shared thread waits for it.
3. The worker's read timeout is set to the request deadline. This limits an individual stalled read, but does not establish a total resource-release bound for trickled responses or blocked writes. Any such bound requires T6 to pass.
4. A worker blocked in an upload write is released by the cleanup thread. Before response headers exist, `disconnect()` goes through `http.closeServer()`, which does not take the stream lock. Test T6 must show this.

**Properties and validation:**
1. Two extension properties. The separate read timeout is dropped: mechanism A has no per-read timeout, and mechanism B derives it from the deadline.
   - `httpConnectTimeoutSeconds`, default `30`
   - `httpRequestTimeoutSeconds`, default `1800`. This is the overall upload deadline and an upper bound for other requests. For status polls and other small GET/POST calls, use an internal effective deadline of `min(60 seconds, httpRequestTimeoutSeconds)`. Multipart uploads retain the full configured deadline. Apply this distinction inside `WsClient`, so both `ReleaseTask` and `CombinedDeployment.resume` receive the short polling deadline through the existing constructor. Use the effective deadline for future waits, request timeouts, fallback read timeouts and timeout messages; do not expose another extension property.
2. Explicit range for both: **1 to 86 400 seconds (24 h)**. Outside the range, fail with `"<name> must be between 1 and 86400 seconds"`.
   - `0` is rejected, because both `URLConnection` and `HttpClient` treat zero or absent timeouts as infinite.
   - Convert with `seconds * 1000L`. The upper bound keeps every value within `int` milliseconds (86 400 000 < 2³¹−1), so the same validated value is safe for `int` setters (mechanism B) and for `Duration` (A). Do not silently clamp.
   - Put the check in a shared `TimeoutSettings.validate(name, value)` helper, so that `ReleaseTask` and any later caller agree.
3. Wire the properties into `ReleaseTask` as `@Input` properties, then into `CentralPortalClient`. Keep the existing 4-arg constructor, which uses the defaults, so `ReleaseAllTask` and the tests keep compiling. `ReleaseAllTask` keeps the defaults in this release; extension timeout overrides apply only to `release`, not `releaseAll`.

**Behaviour to confirm (no code change expected; add assertions to existing tests for the `CentralPortalClient` calls, not the separate `PublicationStatus` availability checks):**
- In the combined flow, a deadline timeout during `CombinedDeployment.submit` must leave an `UPLOAD_ERROR` record, because the outcome is unknown and an automatic re-upload is not safe.
- During `CombinedDeployment.resume`, the same exception is recorded as `lastPollingError` and the poll is retried.

### 2. Make `ReleaseTask` polling tolerate transient errors; fix its messages

**Files:** `ReleaseTask.groovy`

**Retry accounting (keep current behaviour):** today `ReleaseTask` does one initial status check after `initialStatusCheckDelaySeconds`, then up to `statusCheckRetries` further checks while the state is not terminal (`retries-- > 0`, lines 112-120). That means **at most `1 + statusCheckRetries` status requests**. This fix keeps that definition unchanged:
- A failed check (exception) uses the same slot as a check that returns a non-terminal state. Errors never add extra requests.
- `statusCheckRetries = 0` means exactly one status request.
- Update the README text for `statusCheckRetries` to say "number of additional checks after the first one".

**Changes:**
1. Move the status fetch into a private helper that catches `IOException`:
   - `WsException` with status 401 or 403: wrap immediately in a `GradleException` with the same authentication/permission messages used by `createUploadException`, preserving the cause. Share that mapping between upload and status checks; do not sleep or retry.
   - Any other `IOException` (5xx, 429, timeout or deadline from Finding 1, JSON parse failure): log `Status check failed (check n/<1+N>): <message>`, treat the state as unknown (`null`), and continue under the accounting rule above.
2. When all checks are used up and the state is not terminal, replace the generic failure with:
   > `Deployment <id> for <project> is still <state ?: 'unknown'> after <1+N> status checks. It may still publish; check https://central.sonatype.com/publishing/deployments or increase statusCheckRetries / statusCheckIntervalSeconds.`

   If the last check failed, append `Last error: <message>`. Still throw a `GradleException`, so the build does not report success while the outcome is unknown.
3. Keep `"Failed to release ..."` only for the `FAILED` state.
4. Replace `"Failed to find the staging profile id"` (line 103) with `"Central Portal upload returned no deployment id"`.

### 4. Include Gradle Module Metadata and additional artifacts (publications with a main JAR)

- Publications without a main JAR (for example WAR-only and POM-only publications) are rejected by `release` with a clear error before upload.
- Packaging-aware requirements (which primary artifact, and whether sources/javadoc are needed, per packaging) are deferred to a later release with its own plan.

Do not capture `Project` or task instances in task actions.

  caller deadline, covering uploads and deployment status checks for `release` and `releaseAll`, including responses that stall after headers.
  New properties `httpConnectTimeoutSeconds` (default 30) and `httpRequestTimeoutSeconds` (default 1800), each
  1–86400 seconds. Status and other small calls through this client use the shorter of 60 seconds and the configured

  failing a deployment that was uploaded successfully; 401/403 still fail immediately. The number of status checks is
  unchanged: one initial check plus up to `statusCheckRetries` further checks.

  instead of reporting "Failed to release". Replaced the obsolete "staging profile id" error message.

  so `base.archivesName` no longer has to match `artifactId`.

  metadata task with `onlyIf` while the POM still advertises it is now an error. The combined release accepts
  `.module` files in the manifest. Metadata and its signature are cleared before generation to prevent stale
  output from being bundled; generation reruns or restores from cache whenever its task is scheduled. This affects
  all publishing builds, including snapshots, and forces the publication signing task to re-sign every artifact;
  gpg-agent/pinentry may prompt for a passphrase on every publish.
- `release` preserves JAR-producing packaging, including `bundle`, `maven-plugin`, and `ejb`.

- `release` validation now requires a signature and checksums for every artifact in the bundle, not only for a fixed
